## How Mac and Linux results fit together

The three completed Linux summaries record execution commit
`2dbcd505115100f892e906413076ae93b3fcaa16`. That commit is not currently
reachable in this repository. Their numerical outputs remain preserved, but
they are not final-citation-ready until the exact executed revision is made
reachable. This is a provenance recovery task, not an experiment rerun.

- Correctness is an exact tensor-state evaluation rather than a performance
  measurement, so the two distinct macOS correctness protocols may appear in
  one table. They test different cases and are not duplicate trials.
- Robustness uses the Linux 19-case run as the reported result. The macOS run
  repeats the same cases and is supporting cross-platform confirmation only.
  Report `19`, not `38`.
- Scaling and competing-tool timing, memory, and throughput use Linux only.
  The Mac preflights validate harness integration and contribute no paper
  measurements.
- Behavioral inference will use one Linux/CUDA run for all reported models and
  both sides of each comparison. The previous multiply-by-one run is excluded
  from the paper-facing behavioral result.

## 1. Independent correctness and preservation — USE

Paper table: `revision_tests/correctness/results/paper_table.tex`

Ready-to-use result text:

> We evaluated correctness with two independent protocols. Ten hand-verifiable
> cases covered identity serialization, structural edits, metamorphic rename
> and split/concatenate inversions, arithmetic, dtype conversion, and sharded
> save/reload. All 161 tensor--case comparisons matched the independent
> PyTorch oracle exactly, and all 149 tensors outside the declared write-sets
> remained byte-identical. Across pinned GPT-2 124M, OLMo 1B, and Pythia 1B
> checkpoints, all 518 output tensors matched independently computed expected
> values, including all 515 tensors outside the three one-tensor write-sets.
> Deliberately corrupted value, dtype, and key-set controls were detected.

Permitted claim: exact tensor-state correctness and no unintended tensor
changes for the enumerated transformations, formats, and revisions.

Required limitation: custom safetensors header metadata and arbitrary sidecar
files were not preserved, so this is not complete container-level information
preservation and not proof for arbitrary plans. The oracle uses a separate
direct-PyTorch implementation but remains author-written; describe it as an
independent implementation, not an independent third party.

## 2. Robustness and failure semantics — USE

Paper table: `revision_tests/robustness/results/paper_table.tex`

Ready-to-use result text:

> We evaluated 19 failure-semantics cases through the public CLI on Linux. All
> 18 expected non-success outcomes occurred, all 17 applicable diagnostics
> matched, and all 19 source inputs remained byte-identical. All 15 failures
> before publication withheld a new destination or preserved an existing one.
> Three mid-save cases exposed negative behavior: interruption or an injected
> save exception left a partial shard directory, and a fault targeting an
> existing checkpoint produced a mixed directory. Thus 16/19 cases met the
> destination-safety criterion; BrainSurgery does not currently provide atomic
> checkpoint publication.

Permitted claim: source preservation, useful diagnostics, and safe behavior for
the enumerated pre-publication failures.

Required limitation and guidance: write to a fresh destination and accept it
only after successful exit plus independent index/loading validation. Do not
claim transactional, crash-safe, or atomic publication.

## 3. Scaling and systems — USE

Paper table: `revision_tests/scaling/results/linux_2dbcd50/paper_table.tex`

Ready-to-use result text:

> We measured a common weight-scaling and sharded-export operation on ten
> checkpoints spanning 70M--12B parameters, four model families, three dtypes,
> and single-file and sharded inputs. All 150/150 measured outputs passed the
> independent tensor oracle. On the primary within-family Pythia curve, the
> direct Python/PyTorch implementation was faster at every size. At 12B it
> required 15.50 s and 44.77 GiB peak RSS, compared with 24.59 s and 22.88 GiB
> for BrainSurgery in memory and 26.54 s and 28.18 GiB for its arena provider.
> These results show a time--memory trade-off rather than a universal speed
> advantage. GPT-2, OLMo, and Qwen results are reported as separate
> architecture/storage checks rather than pooled into the Pythia scaling curve.

Permitted claim: demonstrated single-process CPU checkpoint rewriting through
12B with measured wall time, process-tree RSS, I/O, throughput, and sharded
output on the recorded Linux host.

Required limitation: this is a CPU/I/O experiment. It provides no GPU-speed,
distributed, optimizer-state, multi-rank, or resharding evidence.

## 4. Competing tools — USE WITH A NARROW CLAIM

Paper table: `revision_tests/competing_tools/results/paper_table.tex`

Ready-to-use result text:

> We compared three genuinely overlapping checkpoint operations on the same
> Linux host, with five measured repetitions per tool and operation. All 30/30
> outputs passed a common independent oracle. For regex key rewriting,
> BrainSurgery required 5.042 s and 1785.7 MiB peak RSS versus 1.478 s and
> 1571.9 MiB for torch-state-bridge. For two MergeKit arithmetic cases,
> BrainSurgery/competitor median wall-time ratios were 1.083 and 1.036, while
> BrainSurgery used 2166.7 versus 2890.4 MiB and 3115.1 versus 3895.3 MiB peak
> RSS, respectively. The comparison therefore shows similar time with lower
> peak RSS in the two MergeKit cases, but a clear disadvantage to
> torch-state-bridge on the tested rewrite.

Permitted claim: correctness and resource measurements for exactly R01, M01,
and M02.

Required limitation: this is not a general ranking, usability result, or proof
of superiority. Orbax remains adjacent related work because its JAX PyTree
restore/resharding abstraction was not a like-for-like executable case.

## 5. Expanded behavioral analysis — COMPLETE, NON-REPORTABLE

The prior paper contained two behavioral comparisons and the revision must
retain both:

1. BrainSurgery versus imperative output: mean PPL ratio, final-token logit
   cosine, absolute logit differences, and top-1 agreement.
2. Original versus forward--backward restored checkpoint: full-sequence mean
   and minimum logit cosine, mean and maximum absolute logit difference, exact
   output agreement, character similarity, token-sequence similarity, and
   token-bag cosine.

The corrected v4 protocol is `revision_tests/behavioral/paper_protocol.yaml`; the
runner is `revision_tests/behavioral/run_cuda_paper_matrix.py`. It expands both
comparisons to the documented 70-prompt suite and ten-model matrix, records all
metrics per prompt, aggregates by model/source/task/language, and produces no
paper table if any measurement is absent. Do not write behavioral result prose
until this run has generated and preserved `evidence.json`.

Run `eacl2027_behavioral_paper_cuda_4cb30d71` completed the full matrix with
finite metrics and exact independent tensor oracles. Every imperative
equivalence comparison passed. The FP32 GPT-2/OLMo and BF16 Qwen round trips
passed, while all four native-FP16 Pythia round trips missed at least one frozen
threshold. The complete sanitized evidence is preserved, but no paper table or
result prose is emitted from this run.

The v4 tensor gate compares the BrainSurgery forward--backward output with an
independent direct-PyTorch forward--backward output. Comparing either rounded
FP16 result byte-for-byte with the original would be an invalid lossless claim.

## Placement in the paper

Suggested main-text order:

1. correctness/preservation establishes semantic validity;
2. behavioral analysis establishes inference consistency on sourced prompts;
3. robustness reports both safe pre-publication failures and non-atomic save
   behavior;
4. competing tools provides narrow external baselines;
5. scaling reports the observed time--memory trade-off through 12B;
6. usability/auditability follows only after the official cohorts complete.

If space is tight, keep compact correctness, behavioral, competing-tools, and
scaling tables in the main paper; move detailed case definitions, per-model
systems rows, robustness case enumeration, and full per-source behavioral
breakdowns to the appendix. Do not detach limitations from the corresponding
main-text claims.
